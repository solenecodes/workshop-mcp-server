MCP workshop · Session 3MCP security best practices
Une situation par carte : - Texte de ticket non fiable : une phrase demandant une autre action reste une donnée, pas une autorisation. L'authentification ne neutralise pas une injection de prompt ; ne pas exécuter d'attaque. - Service trop puissant : confused deputy. Le service ne prête pas ses droits plus larges à un appelant. Moindre privilège et contrôles sur les données cibles. - Action sensible : close_ticket, hypothétique. Droit d'écriture, approbation humaine liée à l'acteur, à l'outil, à la cible et au contenu exact, puis nouvelle vérification avant exécution. - Serveur inconnu : approuver les serveurs, revoir dépendances, versions et changements de descriptions d'outils. readOnlyHint ne remplace pas un contrôle d'autorisation. Question : « Un utilisateur a approuvé la fermeture de CT-1001. L'agent change la cible en CT-1002. L'accord reste-t-il valable ? » Non. Audit : acteur, outil, décision, corrélation, référence d'approbation. Jamais de jetons, secrets, prompts ou résultats bruts.

MCP workshop · Session 3Microsoft Learn · Agent ID
Exemple : Tickets helper (blueprint), tickets-helper-network (instance), responsable réseau (sponsor). Exemples de conception, rien n'est provisionné. - Blueprint : type d'agent et frontière de credentials partagés. - Agent identity : instance distincte, identifiable et attribuable. - Sponsor : responsable qui connaît le besoin et revoit les accès. - Lifecycle : créer, autoriser, revoir, retirer, mettre à la retraite. Déclarer une permission ne l'accorde pas ; consentement et grants restent nécessaires. L'héritage ne concerne que les permissions compatibles et explicitement configurées ; les rôles Azure RBAC sont affectés aux identités individuelles. Agent ID ne bloque pas à lui seul les injections et ne remplace pas l'autorisation sur les données. Clôture : « Le sponsor quitte l'équipe : qui revoit l'agent et ses droits ? » Prévoir revue et retrait ; des jetons émis peuvent rester valides. Désactiver un blueprint partagé peut affecter toutes ses instances. Transition : « Agent ID permet d'identifier l'agent et de lui associer un responsable. Mais avec des dizaines ou des centaines d'agents, comment savoir lesquels existent, suivre leur activité et appliquer les règles de l'organisation ? C'est le lien avec Agent 365 : observer, gouverner et sécuriser les agents à l'échelle du tenant, avec Entra pour l'identité et les accès, Purview pour les données et la conformité, Defender pour les menaces. Ces contrôles ne remplacent pas l'autorisation dans l'API métier. Younes va maintenant présenter cette gouvernance d'ensemble. »

MCP workshop · Session 3Full diagram: last slide
Suivre les deux chemins, sans refaire l'animation OAuth de la session 2. - Délégation / OBO : quand l'API aval doit appliquer les droits d'Alice, l'application obtient un nouveau jeton pour cette API dans son contexte. Registrations, permissions déléguées, consentements et code doivent le permettre. OBO ne crée pas de droits supplémentaires. - Service : le serveur MCP utilise sa propre identité. Chez nous, l'API Tickets est appelée avec l'identité managée et le rôle Mcp.Backend.Read. Un transfert APIM vers MCP pour la même ressource logique n'est pas un échange OBO. Question : « Alice donne l'identifiant d'un ticket d'une autre équipe. Qui vérifie son droit ? » Le service ou l'API qui applique la politique d'accès au record. Un scope de lecture ne suffit pas.
