01
Understand the protocol

A request becomes a tool call.

The AI application decides which tool to use. Its MCP client handles the protocol. The server validates the request and runs the operation.

Read the sequence without animation
  1. The client initializes its connection with the MCP server and negotiates capabilities.
  2. The client sends tools/list. The server returns tool names, descriptions and input schemas.
  3. The application selects list_services or set_service_status for the user's request.
  4. The client sends a structured tools/call request.
  5. The server validates the arguments, then reads or updates the fictitious service store.
  6. The server sends the tool result back. The application uses that result to answer the user.

The client carries the protocol.

It is a component of the host application, not the model itself. An app can connect to multiple MCP servers.

The server does the work.

Tools have typed inputs. The server can call an API, query data or run its own business logic.

A tool can change state.

Select the update scenario above. A confirmation in the app is not a server-side access rule.

ToolsFunctions to query or act
ResourcesRead-only context identified by URI
PromptsReusable interaction templates

This example uses tools over Streamable HTTP. MCP also supports local stdio servers. Resources and prompts are different capabilities; a server does not have to expose all three. MCP complements existing APIs and retrieval systems rather than replacing them.

02
Put a gateway in the request path

Same server. A controlled entry point.

Azure API Management can proxy an existing MCP server. This animation shows a configured rate-limit policy accepting a request—or stopping it before the server is called.

Read the sequence without animation
  1. The client sends its MCP request to the APIM endpoint instead of the backend endpoint.
  2. APIM runs the policies configured for that endpoint.
  3. If the configured rate limit is exceeded, APIM returns HTTP 429. The backend is not called.
  4. Otherwise, APIM forwards the MCP request to the existing server.
  5. The server processes the tool and returns its result through APIM to the client.
  6. Configured diagnostics record the gateway outcome without recording secrets.

A gateway is not a new tool.

The existing tool name and arguments stay the same. The client endpoint changes.

Policies must be configured.

Rate limits, token validation and diagnostics are not implied just by putting APIM in front.

Protect the backend too.

Restrict direct backend access or enforce equivalent controls there, so callers cannot bypass the gateway.

The 10-requests-per-minute limit is an illustrative policy, not an APIM default. The gateway must support the selected MCP version and transport. This is an introduction to the architecture demo, not a deployed APIM configuration.

03
Identify the caller, then check access

Who are you?
And may you change this service?

A protected MCP endpoint needs an appropriate access token. The server must also check scopes and team access before running the tool.

Read the sequence without animation
  1. The client calls the protected MCP endpoint without a token and receives HTTP 401 with a resource-metadata challenge.
  2. The client discovers protected-resource metadata and authorization-server metadata.
  3. The user signs in at the authorization server and consents as required. A public client uses an authorization-code flow with PKCE.
  4. The client exchanges the code with its verifier for an access token intended for this MCP resource.
  5. The client retries the MCP request with that access token.
  6. The resource server validates the token, then checks the required scope and the caller's access to the requested team.
  7. Only an authorized request changes the service. An invalid token is rejected; a valid token with insufficient permissions does not grant access.

Authentication

Establish the caller's identity through the identity provider. The resource server validates the access token.

Authorization

Decide whether that caller can perform this operation on this team's service. A team_id supplied in a request is not proof of membership.

Not token forwarding.

An access token must be intended for its resource. Calling a downstream API requires an appropriate downstream credential, not blindly forwarding the incoming token.

OAuth flow simplified for teaching, based on MCP 2025-06-18. Registration, redirects and discovery details depend on the client and identity provider. MCP connection initialization after authorization is omitted from this animation. services.write and team membership are application-specific example policies, not built-in MCP claims. APIM token validation is a separate deployment choice.

04
Now use a real client

Read. Change. Read again.

During the hands-on exercise, use only the fictitious spaces assigned to your pair. You are using a prepared server, not building one during the exercise.

01 / Connect

Discover the tools.

Add the endpoint provided by the facilitator to VS Code. Inspect list_services and set_service_status.

02 / Observe

Read the current state.

Record the service ID and original status. Do not assume the model's answer proves an operation happened.

03 / Execute

Confirm the change.

Request maintenance, inspect the arguments and approve the write. Read again to verify it.

04 / Restore

Leave the data as it was.

Restore the original status and verify it with another read. Discuss where an access check should occur.
