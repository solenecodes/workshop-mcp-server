Course · Lesson 1 of 6 · 2 minutes

1. What is MCP?

The Model Context Protocol is a standardized communication protocol that connects AI applications to external data sources and tools. Without a common interface, each integration needs a custom connector: an N × M problem, where N tools × M AI applications can mean hundreds of separate connectors.

MCP turns this into an N + M integration model: each system exposes an MCP server, and each AI application implements an MCP client. Both sides communicate through the standard protocol. You can reuse an integration across compatible applications such as VS Code with GitHub Copilot or Microsoft Copilot Studio, while still checking supported features, configuration and access permissions.

2. The USB-C analogy

The most common analogy, also used by Anthropic, is USB-C:

🔌

Before USB-C

Each device had its own cable: micro-USB, Lightning, mini-USB or a proprietary connector. One connector could not connect everything.

⚡

With USB-C

A common connector for chargers, displays and accessories. The device and cable must still support the feature you need.

🤖

Before MCP

Each AI application had its own custom integrations. Connecting Claude to Slack was not the same integration as connecting ChatGPT to Slack.

🔗

With MCP

A Microsoft Fabric MCP server can be reused by compatible applications such as VS Code with GitHub Copilot or Microsoft Copilot Studio. One shared protocol, multiple clients, subject to their supported features and authentication requirements.

3. Architecture: client, server, host

MCP uses a client-server architecture with three main components:

Architecture: the three participants
ComponentRoleExamples
HostThe AI application you use.Claude Desktop, ChatGPT, Cursor, VS Code.
MCP clientThe module inside the host that speaks MCP: one per server connection.Built into the host, usually invisible to the user.
MCP serverThe connector to a tool or data source.A GitHub server, a PostgreSQL server, or our Tickets server.

Scroll the table sideways, or focus it and use the arrow keys.

The flow is simple: you ask the assistant, “What is ticket CT-1001 about?” The host uses the model API, not MCP, to obtain a tool proposal. Its MCP client then sends the approved request to the Tickets MCP server, which checks access, calls the ticket API and returns the result. These protocol messages use JSON-RPC 2.0.

🔄 Transport: MCP supports stdio for local servers running on your machine, and Streamable HTTP, introduced in March 2025, for remote servers. The older HTTP+SSE transport was replaced by Streamable HTTP.

4. The 3 primitives: Tools, Resources, Prompts

MCP servers expose their capabilities through three types of primitives. A server does not have to implement all three:

Three kinds of server capability
PrimitiveWhat it isConcrete example
ToolsActions the model can request, subject to application and server controls.create_issue, send_message, run_query
ResourcesData the application can read and provide as model context.File contents, a database schema, a list of Slack channels.
PromptsPredefined instruction templates that the user can select.“Analyze this code” or “Summarize this pull request”.

Scroll the table sideways, or focus it and use the arrow keys.

Tools are the focus of this workshop. When you connect a GitHub MCP server, a compatible host can discover the available tools, such as creating a pull request, reading files or searching issues, and offer them to the model for the task at hand.

Our live Tickets server implements tools only: list_tickets and get_ticket, using tools/list → tools/call. The resource and prompt examples above are illustrative, not extra demo endpoints; their corresponding methods are resources/list → resources/read and prompts/list → prompts/get.

5. Timeline: from launch to October 2026

  1. November 2024

    Anthropic announces MCP as an open standard, with TypeScript and Python SDKs and initial reference servers.

  2. March 19, 2025

    Microsoft introduces MCP support in Copilot Studio, connecting agents to existing knowledge sources and APIs through MCP servers.

  3. March 26, 2025

    A new specification revision introduces Streamable HTTP, replacing the earlier HTTP+SSE transport, and an HTTP authorization framework.

  4. Summer 2025

    MCP support becomes generally available in VS Code 1.102, extending GitHub Copilot with external tools and data sources.

  5. November 2025

    The specification adds experimental tasks for durable requests with polling and deferred results, alongside authorization and interaction improvements.

  6. December 2025

    Anthropic contributes MCP to the Agentic AI Foundation (AAIF) under the Linux Foundation, alongside founding projects from Block and OpenAI.

  7. February 2026

    97 million monthly SDK downloads. 1,200+ public MCP servers. MCP is the de facto standard for AI connectivity.

  8. September 2026

    Foundry catalog snapshot, checked October 20, 2026: 1,000+ connectors from Microsoft (SharePoint, Teams, Dynamics 365), verified third-party publishers (Docusign, Databricks, Box), and independent publishers.

6. MCP vs Function Calling

Function calling is the established approach for connecting a model to tools: the model proposes a function name and structured arguments. MCP standardizes how applications discover and use server capabilities. Here are the key differences:

Function calling and MCP: compare their responsibilities
CriterionFunction callingMCP
StandardModel-provider interfaces; formats and features can differ.Open client-server protocol.
PortabilityThe application adapts tool definitions to each model interface.One server can serve multiple compatible clients.
Tool discoveryThe application supplies the tool definitions to the model.The client discovers the server's available tools.
ExecutionThe developer handles execution in the application. A proposal is not execution.The MCP server validates the request and executes the allowed operation.
ScalabilityThe application manages its tool catalog and integrations.Modular: connect or disconnect servers and discover their capabilities.
Best suited forModel-driven tool use, from a quick prototype to production.Reusable integrations across compatible applications. No LLM required to speak MCP.

Scroll the table sideways, or focus it and use the arrow keys.

In short, function calling and MCP complement each other: the model proposes, the host checks, and the server executes. MCP is useful when you want portable integrations shared by multiple compatible applications; function calling is not limited to simple prototypes.
