Why it matters

An MCP server is a new way into your data

This morning: an open door

  • Anyone with the URL can call it
  • The URL ends up in config files: it is not a secret
  • Fine for synthetic tickets, not for real data

The enterprise answer: one front door

  • An Entra token for this API, with Mcp.Read
  • A call budget per person
  • One address in the inventory, never the backend

Agents call tools fast and at scale. You secure the door, once, not every server.

Lesson 1 · Four decisions per MCP server

Every MCP server asks four questions

Host

Where does it run? Container Apps here; Functions, App Service or AKS elsewhere.

Expose

How do clients reach it? Through one gateway that checks identity.

Discover

How do teams find it? API Center or the Foundry private tool catalog.

Consume

Who uses it, with whose rights? VS Code, agents, apps.

The team owns the code and where it runs. The platform owns the door, the identity and the inventory.

Lesson 5 · Two ways to expose with API Management

Write MCP code only when tools need logic

Pattern B · REST API as MCP

  • The gateway turns each operation into one tool
  • No MCP code to write or host
  • Tools only, one operation per tool (Preview)

Choose it when the API exists and tools are simple reads.

Pattern A · existing MCP server

  • Forwarded as is; the server checks the same token again
  • Tools and resources, not prompts
  • Keeps its own logic and identity

Choose it when tools orchestrate several calls or need an identity.

Either way: register the gateway address in the inventory, never the backend.

Lesson 5 · Pattern B up close

A virtual MCP server from an API you already have

Existing REST API in API Managementany HTTP-compatible API, incl. APIs imported from Azure resources pick
operations → MCP server on the gatewayone operation = one tool · no MCP code tools/list → VS Code, Copilot Studio, agentsdiscover and call the tools

What you get

A façade: the API stays as is. Policies on the MCP server apply to every tool: token, quota, logs. Change the exposed operations later in the Tools blade.

Limits

Tools only, no resources or prompts. HTTP-compatible APIs only. Not in workspaces. Never read the response body; log 0 bytes of it.

In our workshop

contoso-tickets-mcp is built from contoso-tickets. That API is answered by a gateway policy: a façade over synthetic data, no backend at all.

MCP workshop · Session 2Microsoft Learn · Expose a REST API as an MCP server
Message: API Management can turn an API you already manage into an MCP server without writing MCP code. A "virtual" or façade MCP server. From Microsoft Learn (Expose REST API in API Management as an MCP server): any HTTP-compatible API managed in API Management, including APIs imported from Azure resources; select one or more operations as tools; tiers include Basic v2. Limits: tools only (no resources or prompts), not available in workspaces, do not access context.Response.Body in MCP policies, set frontend response payload logging to 0 bytes at the All APIs scope. In production the REST API points to the real backend. If the backend needs credentials, attach them in a gateway policy, never in the client (Learn troubleshooting: the Authorization header is not forwarded automatically). In our workshop, the REST API is answered by a return-response policy with the three synthetic tickets: proof that the MCP server is purely a façade. 3 minutes.

Lesson 6 · Before a business unit connects agents

Five checks, and two gaps we know

Five checks

  1. Who may grant consent to apps and agents?
  2. Who may add MCP servers? Prefer the private catalog.
  3. Agent identities: an owner and an expiry, like apps.
  4. Data leaving the tenant: approve each third-party server.
  5. Logs and cost: metadata only, tagged owners.

Not closed yet

  • The protected Container App still answers a valid token directly. Restrict its ingress to the gateway.
  • No live 403 in the demo: Azure CLI always gets Mcp.Read.
