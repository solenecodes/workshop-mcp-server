Why use MCP?

What changes — and what does not?

The server is code you run, not the model and not a central MCP service. This diagram shows one server wrapping several systems; an application can also connect to several servers. Developers still implement the backend connectors, access checks and business rules.

MCP means Model Context Protocol: an open standard for exchanging context and calling capabilities. It does not give the model automatic access to everything.

How do I connect?

Add a trusted server to your application's MCP settings: a command for a local process, or an endpoint URL for a remote server. Review the permissions and credentials, then inspect the capabilities it exposes. We will do this in the lab.

Technical terms: stdio connects local processes; Streamable HTTP connects an HTTP endpoint. MCP messages use JSON-RPC 2.0. Each server connection has its own MCP client inside the host.

Servers may expose tools, resources, prompts, or a subset. Client support varies; the workshop backend implements tools.

How is MCP different from an API?

Your API still does the work. An MCP server makes selected operations discoverable and callable by compatible AI applications.

Business API

Exposes a service's operations

Your code must know the endpoint, required inputs and authentication. Example: a document-search endpoint.

Implemented for this service
MCP server

Exposes tools to an AI application

The client discovers a “Search documents” tool and its inputs. The server translates the call into the existing search operation.

One protocol across compatible clients
AI app→ MCP server→ Existing API→ Data

One possible architecture. A server can call an API or work with files and data directly.

API Business operations.

MCP Standardized discovery + interaction.

RAG Retrieval to ground an answer.

Can an API also describe itself?

Yes: OpenAPI can describe a REST API. MCP is not the invention of typed APIs. It defines a shared interaction protocol for compatible AI applications, including capability discovery and invocation. Developers still implement connectors and authorization; MCP does not train the model or make every tool safe.

Real Entra vs the local teaching model

The local server accepts public demo tokens. It does not perform Entra sign-in, JWT validation, OAuth discovery or OBO. A real protected MCP resource needs issuer, signature, lifetime and audience validation plus the right scopes and business policy. A downstream API needs its own audience token; do not forward the MCP token blindly.

Delegated/OBO: the downstream call retains user context. Application identity: the service uses its own permissions. Neither is implemented in this local demo.
