09:20–09:30 · Pourquoi MCP ?

Le modèle ne connaît pas
le statut de votre service.

Pour répondre avec une donnée actuelle ou agir sur un système, l’application doit se connecter à une capacité externe.

02
Sans accès à une source

Une réponse n’est pas une observation.

« Le service Catalogue est-il disponible ? »

Le texte produit par le modèle ne prouve ni l’état du service ni qu’une action a été exécutée.

Avec un outil adapté

Lire l’état, puis répondre.

Intention→list_services→Donnée

Le client exécute un appel et fournit le résultat au modèle. La réponse peut alors s’appuyer sur cette observation.

Model Context Protocol

Un protocole ouvert pour connecter des applications d’IA à des outils et à des sources de contexte, via une interface standardisée.

MCP standardise l’échange. Il ne remplace pas votre API et ne crée pas les droits d’accès.

Système métier

API, données, services

La source et la logique restent ici. Le serveur peut aussi porter sa propre logique.

Un hôte peut gérer plusieurs clients MCP, chacun associé à un serveur. Le serveur peut être local ou distant.

API

RAG

MCP

Notes d’animation · architecture

Demander : « Le serveur MCP est-il le modèle ? » Non. Montrer que le client est un composant de l’hôte, pas nécessairement une application séparée. MCP réduit la diversité des interfaces d’intégration côté client ; chaque serveur doit toujours implémenter sa logique métier et sa sécurité.

09:30–09:40 · Le vocabulaire utile

Trois capacités, trois intentions.

Un serveur ne doit pas toutes les implémenter. Leur prise en charge dépend aussi du client.

03
Agir ou interroger

Tools

Des fonctions avec un nom, une description et un schéma d’entrée. Le modèle peut proposer un appel ; le client pilote son exécution.

list_services(team_id)

Un outil peut être en lecture seule ou modifier un état.

Fournir du contexte

Resources

Des contenus identifiés par une URI, que l’application peut lire et intégrer au contexte.

catalog://services/schema

Exemple de ressource, pas un endpoint de cet atelier.

Guider une interaction

Prompts

Des modèles d’instructions exposés par le serveur, que l’utilisateur peut sélectionner dans un client compatible.

analyser_un_incident

Un prompt n’accorde aucune permission métier.

Notre fil rouge utilise des tools. Les resources et prompts ci-dessus sont des exemples explicatifs, pas des capacités déjà implémentées.

Même protocole, deux chemins de transport

Processus local

stdio

Le client communique via l’entrée et la sortie standard du processus serveur.

Client↔Processus local

Local ne veut pas dire sûr : vérifier le code exécuté et ses accès.

Serveur distant

Streamable HTTP

Les échanges passent par HTTP ; le serveur peut être utilisé par plusieurs clients.

Client↔Endpoint HTTPS

Le transport du serveur fil rouge ; HTTPS seul ne définit pas les droits.

Le schéma fait partie du contrat. Une description claire aide à choisir l’outil ; le serveur doit quand même valider les arguments. Ni une description ni une annotation de lecture seule ne remplace une politique d’autorisation.

04
Connexion et capacités

Le client établit l’échange.

Il identifie les capacités et la version compatibles avec le serveur. La séquence exacte dépend de la version du protocole et du client ; laisser le SDK ou Inspector la gérer.

Client MCP↔Serveur d’atelier

Pour la démo, vérifier les versions réellement utilisées plutôt que réciter une capture d’une autre version.

tools/list

Que sais-tu faire ?

Le serveur retourne les noms, descriptions et schémas des outils disponibles pour cette connexion.

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

Le modèle peut utiliser les descriptions pour proposer un outil. La liste visible ne prouve pas à elle seule qu’une autorisation métier est appliquée.

tools/call

Lis les services de cette équipe.

Le client envoie un nom d’outil et des arguments structurés. L’outil n’exécute pas directement la phrase de l’utilisateur.

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "list_services",
    "arguments": { "team_id": "team-demo" }
  }
}
Réponse au même id : 2

Un résultat observable, pas une promesse.

Exemple de réponse MCP avec un contenu texte contenant une donnée fictive. Le client peut ensuite l’utiliser pour répondre.

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [{
      "type": "text",
      "text": "{\"services\":[{\"service_id\":\"svc-catalog\",\"team_id\":\"team-demo\",\"name\":\"Catalogue\",\"status\":\"healthy\"}]}"
    }]
  }
}

Un résultat d’outil peut aussi signaler un échec. Le résultat réel doit être contrôlé et les erreurs rendues visibles.

Messages JSON-RPC 2.0 illustratifs. Ce ne sont pas des requêtes HTTP complètes : le client gère aussi les règles du transport et du cycle de connexion.

Notes d’animation · faire lire un échange

Demander au groupe de retrouver le nom de l’outil, ses arguments, puis l’identifiant qui relie requête et réponse. Faire distinguer la donnée retournée de la reformulation du modèle. Ne pas faire passer ce parcours interactif pour une démo live.

06
État de préparation : le serveur et son hébergement restent à construire. L’exercice sera réalisable après validation et distribution du point d’accès par l’animation. Aucun endpoint opérationnel n’est intégré à cette présentation.
Contrat proposé

Un catalogue 100 % fictif.

Deux espaces jetables par binôme, par exemple team-07-a et team-07-b, et seulement deux outils :

list_servicesLire les services d’un espace
set_service_statusModifier le statut d’un service

Statuts : healthy, degraded, maintenance. Identifiants illustratifs : utilisez ceux distribués à votre binôme.

Preuves attendues

Pas juste « c’est fait ».

  • Les deux outils sont visibles dans le client.
  • Un appel de lecture fournit l’état initial.
  • Une écriture est confirmée, puis vérifiée par relecture.
  • Les deux espaces attribués sont testés.
  • Les statuts initiaux sont restaurés et relus.

10:05–10:15 · Le vrai apprentissage

Confirmer un appel
n’est pas autoriser un accès.

07
Côté client

« Je confirme cette action. »

La confirmation porte sur l’exécution dans ce client. Masquer un outil ne protège pas le serveur contre un autre client.

Côté serveur

« Cette identité a-t-elle ce droit ? »

Le serveur doit vérifier les accès aux données et les opérations autorisées. Un team_id fourni dans l’appel n’est pas une identité.

Question au groupe

Je désactive l’outil d’écriture dans mon client.
Est-il désormais inaccessible à tous ?

Afficher l’explication

Non. Le masquage ne concerne que ce client. Un autre client pourrait appeler l’outil si le serveur l’accepte. L’autorisation doit être contrôlée côté serveur et le backend ne doit pas permettre de contourner la protection annoncée.

L’atelier illustre une absence volontaire de contrôle par équipe dans un bac à sable. Il ne prouve pas que tous les serveurs MCP sont ouverts.

Notes d’animation · débrief

Faire raconter une preuve par un binôme : état initial, appel, relecture. Demander ce que le serveur sait réellement de l’appelant. Distinguer authentification, autorisation et confirmation. Ne pas anticiper la présentation indépendante de la session 3 ; préparer la transition vers les briques sur notre serveur commun.

Choix de l’intervenant

Par exemple, APIM devant le serveur.

La session 2 choisit ses briques et son scénario sur le socle commun. Une passerelle peut changer le point d’accès et les contrôles appliqués, sans recréer le cas métier.

Client→APIM, si retenu→Même serveur MCP

Option d’architecture, pas une infrastructure déjà déployée. L’URL et l’authentification peuvent changer.

Selon l’état laissé par la session 2

Compléter, pas refaire.

Identité, droits métier, délégation ou supervision : sélectionner les briques restantes et rejouer les mêmes outils pour vérifier les appels autorisés et refusés.
