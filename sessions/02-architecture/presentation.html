Why these four?

  1. This morning: one open door. Anyone with the address could call the server. Fine for synthetic tickets, not for real data.
  2. Next session: a badge on the server. The protected server asks for a Microsoft Entra token with Mcp.Read.

  6. No badge, no entry. Without a token the door answers 401 and says where to sign in.

  8. Let other teams find it. The door address goes in the inventory, never the server address.

One address. One badge per API. The servers stay behind the door.

Course · Lesson 4 of 5

Two ways to expose MCP
with API Management

Both give clients the same tickets with the same badge. They differ in who writes the MCP code.

Pattern A · existing MCP server

Put the server you run behind the door

The protected Container App keeps its code and checks the token again. Tools, and resources or prompts if the server offers them.

Choose it when tools need their own logic
Pattern B · REST API as MCP

Turn API operations into tools

Nobody writes MCP code: list_tickets → GET /tickets, get_ticket → GET /tickets/{ticketId}. Tools only, one operation each.

Preview · choose it for a stable REST API

The same controls in both patterns

  • One badge per API. A Microsoft Entra token for this API only, then Mcp.Read. No token: 401. No Mcp.Read: 403.
  • A call budget per person. Too many calls: 429 with a retry time.
  • One public address. Clients and the inventory only know the gateway URL.
  • No subscription key. Access depends on the token, never on a shared key.
Good to know before you build

MCP servers work on the Developer, Basic, Standard and Premium tiers, and on Basic v2, Standard v2 and Premium v2. They are not available in API Management workspaces.

Infrastructure as code uses API version 2025-09-01-preview (Preview). Policies on an MCP server must never read the response body: it would break streaming.

In pattern A, the server stays reachable at its own address unless its network only accepts the gateway. Close that door before you promise “gateway only”.

Same door, different clients

GitHub Copilot in VS Code, Foundry Agent Service and Copilot Studio call the same gateway URL. Only the identity changes: the user’s, or the agent’s own.

Badge per caller
Five checks before a business unit connects agents
  1. Consent. Who may grant consent to applications and agents?
  2. Who may add MCP servers. Prefer the private catalog over free-form URLs.
  3. Agent identities. Inventory them like applications, with an owner and an expiry.
  4. Data leaving the tenant. Approve each third-party MCP server like a SaaS application.
  5. Logs and cost. Tool name, caller, status and latency only. Tag owners and expiry dates.
