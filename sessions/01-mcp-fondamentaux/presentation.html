The idea in 30 seconds

An assistant cannot infer your live business data or safely invent API calls. A developer exposes explicit capabilities through a server. A compatible host discovers those capabilities and decides when to use them. MCP standardizes that exchange; each backend still needs an implementation and its own security.

The lines are connections, not a central MCP service. Hosts implement an MCP client; each system exposes its own server.

What MCP does not decide

It does not train the model, choose your business policy, replace every connector, or make a tool automatically safe. A REST API can also have discovery specifications such as OpenAPI. MCP supplies a runtime interaction protocol that compatible hosts understand; developers still implement the integration and authorization.

  1. No valid credential: HTTP 401, no business operation.
  2. A server-trusted identity determines roles and assignments.
  3. The server checks the tool allowlist and claim assignment.
  4. Reader results are minimized; a different customer's claim is denied.
  5. Writes produce an expiring proposal. A different human-controlled supervisor/admin identity must confirm it.

Real Entra vs the local teaching model

The local server accepts public demo tokens. It does not perform Entra sign-in, JWT validation, OAuth discovery or OBO. A real protected MCP resource needs issuer, signature, lifetime and audience validation plus the right scopes and business policy. A downstream API needs its own audience token; do not forward the MCP token blindly.

Delegated/OBO: the downstream call retains user context. Application identity: the service uses its own permissions. Neither is implemented in this local demo.
